### Q2. How would you design a C++ application on the safety MCU for system monitoring and fault handling?

For a **C++** application running on a safety **microcontroller**, my first step is to model a clear separation between the **hardware abstraction**, **fault detection logic**, and **reporting interface** to the higher‑level autonomous driver. On an **ARM Cortex‑M** or **AURIX‑class** MCU, I would design a thin HAL layer that provides access to peripherals like watchdog, timers, voltage monitors, and communication interfaces such as **CAN/CAN FD** without exposing low‑level register details to the rest of the code. This aligns with how I previously developed reusable **HAL components**, which significantly reduced integration effort across hardware variants.

Above the HAL, I would define **C++ classes** representing individual health monitors—for example, `PowerMonitor`, `CommMonitor`, and `TaskHealthMonitor`. Each class would encapsulate thresholds, sampling strategies, and debouncing logic to avoid false positives. Using RAII and strong typing in **C++**, I can enforce initialization of critical resources and ensure that monitoring hooks are always called, even during error paths. On top of that, I would implement a `FaultManager` component that aggregates raw events into standardized fault records, assigns severity levels, and maps them to diagnostic codes compatible with existing **UDS** or internal fault protocols.

Communication with the virtual driver or base vehicle would go through a structured messaging layer over **CAN FD** or a similar internal bus. Here, my previous experience mapping signals into **DBC** files and configuring **ECU network communication** is useful, because I can ensure that each fault and health status is encoded efficiently and reliably. To make the system testable, I would design clear interfaces so that the same monitoring logic can be exercised in **SIL** and **HIL** environments using **Vector CANoe** and **CAPL**, where we can simulate voltage drops, communication timeouts, and task overruns, verifying that the safety MCU responds deterministically and reports consistent fault information to the higher‑level system.


### Q3. Describe your experience with CAN / CAN FD and how you would debug a communication issue in a Torc truck.

I have extensive hands‑on experience with **CAN** and **CAN FD** in both my positions at **General Motors** and **Robert Bosch Engineering**, working across multi‑ECU automotive platforms. When debugging a communication issue in a truck, I start with observability. Using **Vector CANoe** and an oscilloscope, I verify physical layer integrity, checking for dominant/recessive level issues, termination, and noise. Once the physical layer looks healthy, I inspect message traces to confirm identifiers, DLC, and timing against the specification. If the issue is related to diagnostics over **UDS**, I verify service request and response sequences, session control, and security access timing. In one project, this approach helped reduce diagnostic session failures by **22 instances per release cycle** by identifying mismatches in timing expectations between ECUs.

On the firmware side, I instrument the **C/C++** code around the CAN driver and communication stack, in some cases enabling temporary logging over a secondary channel such as UART. I verify configuration aspects like filter masks, interrupt priorities, and buffer management to ensure that frames are neither dropped nor overwritten under load. If the system uses **AUTOSAR**‑style configuration, I cross‑check **DBC configuration** and routing tables to confirm that all signals are correctly mapped. Finally, I re‑run automated integration scenarios in **HIL/SIL** environments to validate that the fix holds under stress, including worst‑case bus load and fault injection such as forced error frames or missing messages.

### Q5. Explain a situation where you optimized memory or stack usage on an ARM Cortex‑M system.

In my current role at **General Motors**, I worked on a **bare‑metal ARM Cortex‑M** platform where memory was extremely constrained, and we needed to integrate additional control logic without changing hardware. The initial firmware exhibited sporadic stack overflows under worst‑case load, which manifested as random resets and corrupted variables. My first step was to instrument stack usage, enabling stack pattern filling and monitoring high‑water marks in different tasks and interrupt contexts.

Using this data, I refined the **linker script** to allocate stack and heap more appropriately, and I analyzed large local variables and recursion in the **C/C++** code base. Where possible, I moved large buffers to static or global scope and reduced unnecessary dynamic allocation. I also restructured some algorithms to use fixed‑size arrays and bitfields to minimize RAM usage, which is particularly important on **ARM Cortex‑M** architectures with tight SRAM limits.

Another optimization was to review interrupt priorities and execution times. By shortening critical ISRs and deferring non‑urgent work to lower‑priority contexts, I reduced worst‑case stack depth. After these changes, we reclaimed around **48 KB** of memory, which allowed us to integrate new application features and improved logging. The stack overflow issues disappeared in stress tests, and there were no related field failures in subsequent releases. This experience makes me comfortable working within the resource constraints typical of a safety **MCU** in Torc’s compute platform.

### Q12. Describe a particularly challenging bug you encountered and how you resolved it.

One challenging bug I encountered involved intermittent resets on a **bare‑metal ARM Cortex‑M** ECU in a distributed control system. The issue appeared only under high communication load, and initial traces showed random behavior, which made it difficult to reproduce consistently. My first step was to instrument the firmware with additional logging over a secondary interface and to enable detailed stack and memory checks, including stack pattern filling and periodic integrity checks.

Using **Vector CANoe** to generate worst‑case **CAN FD** traffic and stress the system, I reproduced the resets more frequently. Analysis of logs and memory dumps indicated a stack corruption pattern associated with a particular diagnostic routine. On reviewing the **C** implementation, I found that a large local buffer was being allocated on the stack inside a function that could be called from both normal and elevated priority contexts, leading to excessive stack usage in some scenarios. Additionally, there was a corner case where an index was not properly bounded.

I refactored the routine to use a statically allocated buffer with proper access synchronization and introduced strict bounds checking on all indices. I also adjusted stack sizes in the **linker script** based on updated measurements. After these changes, I reran the same stress tests and observed no further resets. The fix was validated through extended regression testing and later confirmed in vehicle testing, with no related field issues reported. This experience reinforced my habit of combining systematic instrumentation, worst‑case testing, and careful code review when dealing with complex embedded bugs.

### 1. Linux Fundamentals

**What is Linux?**
A **Unix‑like kernel** plus user‑space tools and libraries, typically packaged as a **distribution** (Ubuntu, Debian, etc.). The kernel manages hardware, processes, memory, and devices; user space hosts shells, daemons, and applications.

**Key concepts**

- Kernel vs user space
- Processes and threads
- System calls and file descriptors
- Everything is a file (devices, sockets, pipes)

```bash
# Check kernel version
uname -r

# Show basic system info
uname -a
```



### 2. Filesystem Hierarchy \& Paths

Common directories:

- `/` root of filesystem
- `/bin`, `/sbin` core binaries
- `/etc` configuration
- `/home` user directories
- `/var` variable data (logs, spool)
- `/dev` device files
- `/proc`, `/sys` virtual files exposing kernel info

```bash
# List root directories
ls /

# Show current directory
pwd
```

Understanding absolute vs relative paths is essential when scripting and working on remote systems.

```bash
less long_file.log
```

Text processing is crucial in logs and automation:

```bash
# Filter lines containing 'ERROR'
grep 'ERROR' app.log

# Column extraction
awk '{print $1, $3}' data.txt

# Replace text in stream
sed 's/old/new/g' config.txt
```



### 4. Users, Groups, and Permissions

Each file has owner, group, and permission bits: read `r`, write `w`, execute `x`.

```bash
# Show detailed permissions
ls -l

# Change permissions: rwxr-xr-x
chmod 755 run.sh

# Change owner and group (root only)
sudo chown user:group file
```

Execute bit matters for binaries and scripts. In embedded contexts, device nodes in `/dev` often require correct groups (e.g., `dialout`, `video`) for access.


### 5. Processes, Jobs, and Signals

A **process** is a running program instance with its own PID.

```bash
# List processes
ps aux

# Top CPU/memory usage
top    # or htop if installed

# Kill a process by PID
kill 1234           # SIGTERM
kill -9 1234        # SIGKILL
```

Foreground/background control in shells:

```bash
# Run in background
./long_task &

# Stop and resume
Ctrl+Z       # suspend
bg           # resume in background
fg           # bring to foreground
jobs         # list jobs
```

Signals like `SIGINT`, `SIGTERM`, `SIGKILL` control process behavior. In embedded Linux, understanding signal handling is important for daemons and graceful shutdown.


### 6. Systemd and Services (Typical Desktop/Server)

Modern distros use **systemd** for service management.

```bash
# Check service status
systemctl status myservice

# Start / stop / restart
sudo systemctl start myservice
sudo systemctl stop myservice
sudo systemctl restart myservice

# Enable at boot
sudo systemctl enable myservice
```

For embedded platforms, you may see **systemd**, **init scripts**, or custom startup frameworks.


### 7. Package Management

Different distributions use different tools.

Debian/Ubuntu:

```bash
sudo apt update
sudo apt install build-essential gdb
sudo apt remove package_name
```

Red Hat/CentOS/Fedora:

```bash
sudo dnf install gcc-c++ gdb
```

On embedded systems, you might use **Yocto**, **Buildroot**, or vendor‑specific package managers instead of full desktop ones.

### 13. Compiling and Building C/C++ Code

Using **gcc/g++** directly:

```bash
# Compile C++
g++ -Wall -O2 main.cpp -o main

# Compile with debug info
g++ -g main.cpp -o main_debug
```

Using **Make**:

```make
# Makefile snippet
CXX=g++
CXXFLAGS=-Wall -O2

all: app

app: main.o
	$(CXX) $(CXXFLAGS) main.o -o app

clean:
	rm -f *.o app
```

Then:

```bash
make
make clean
```

On embedded targets, cross‑compilers (`arm-none-eabi-gcc`, etc.) are used, and build systems like **CMake** or **Yocto** integrate toolchain configuration.


### 14. Debugging with gdb

**gdb** is the standard debugger.

```bash
# Compile with debug symbols
g++ -g main.cpp -o main

# Run under gdb
gdb ./main
(gdb) break main
(gdb) run
(gdb) bt        # backtrace
(gdb) print x
(gdb) step / next
```

For embedded Linux, you can use `gdbserver` on the target and connect from the host.

```bash
# On target
gdbserver :1234 ./app

# On host
gdb ./app
(gdb) target remote target_ip:1234
```



### 15. Tracing with strace and ltrace

`strace` traces system calls; `ltrace` traces library calls.

```bash
# Trace syscalls
strace -o trace.log ./app

# Follow a specific syscall
strace -e openat ./app
```

These tools are powerful when you need to understand why a process cannot open a file, connect to a socket, or access a device.


In embedded environments, you may also use `perf` or vendor tools to profile CPU usage and identify hotspots in **C/C++** applications.


### 17. Logging and System Diagnostics

System logs are usually under `/var/log`.

```bash
# View kernel messages
dmesg | tail

# Follow a log file
tail -f /var/log/syslog
```

On embedded systems, logs might be redirected to serial ports, custom files, or network sinks, but the analysis principles remain the same: filter, correlate timestamps, and connect symptoms to code changes.


### 18. Devices, udev, and Permissions

Device files in `/dev` represent hardware.

```bash
ls -l /dev

# Check group and permissions
ls -l /dev/ttyUSB0
```

**udev** rules can assign permissions and symlinks based on device attributes. For example, a rule to give user access to a USB device might match vendor and product IDs and set group ownership appropriately.

Understanding this is important when your application interacts with serial ports, CAN interfaces, or custom hardware under **Linux**.


### 19. Embedded Linux and Cross‑Compilation

Embedded Linux often runs on ARM or other architectures with smaller resources.

Key concepts:

- Root filesystem, kernel image, bootloader (e.g., **U‑Boot**)
- Cross‑compilation toolchains
- Build systems like **Yocto** or **Buildroot**

```bash
# Example cross-compile
arm-none-eabi-gcc -mcpu=cortex-m4 -O2 main.c -o main.elf
```

Even when your main firmware is bare‑metal, you might use embedded Linux boards in HIL setups or as gateways, so understanding build and deployment flows is helpful.


### 20. Linux Boot Process (High‑Level)

Typical stages:

1. Firmware/BIOS/boot ROM initializes hardware.
2. Bootloader (e.g., GRUB, U‑Boot) loads the kernel.
3. Kernel initializes drivers, mounts root filesystem.
4. `init` or **systemd** starts user‑space services and targets.

In embedded contexts, customizing bootloader and kernel command line parameters is common to control console output, rootfs location, and init system behavior.
